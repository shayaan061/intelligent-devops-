D. PAGES 2-4: PRIOR ART
-------------------------------------------------------------------------------------
D1. New subsection "6) Existing AI-assisted operations tools":
-----
Recent tools such as k8sgpt, HolmesGPT and Datadog Bits AI apply LLMs to diagnose
infrastructure problems. These tools mainly explain or summarize issues, and either leave
remediation to the engineer or carry out actions without a separate, deterministic safety
layer. They also do not combine rule-based and ML-based detection into a common incident format
with runbook fallback, or bound re-analysis using the history of attempted actions. Statistical
anomaly detection methods (e.g., Isolation Forest, Liu et al., ICDM 2008) and graph-based
root-cause methods (e.g., MicroRCA, Wu et al., NOMS 2020) detect or localize faults, but do not
generate and safely execute a verified remediation.
-----

D2. Add to "4) Limitations of Existing Systems":
-----
- Threshold rules cannot detect gradual or multi-metric deviations (for example, a slow memory
  rise) before a hard limit is reached.
- In multi-service systems, the alerting service is often only a downstream symptom, not the
  root cause.
- Applying LLM output directly to infrastructure is unsafe without validation, because LLMs can
  produce incorrect or hallucinated actions.
-----

D3. Add to "5) Gap and Motivation":
-----
There is a need to use LLM reasoning for incident response while guaranteeing that no
unvalidated action reaches the infrastructure, and that remediation attempts are bounded and
verified.
-----

E. NEW SECTION BEFORE "DISCLOSE WORKING OF INVENTION" (PAGE 5)
-------------------------------------------------------------------------------------
-----
Summary of the Invention and Technical Advancement

The invention provides the following technical advancements over existing systems:

1. Dependency-aware context builder. When an event is received, the system automatically
   collects the metrics, container states, restart counts and recent actions of all services in
   the dependency chain of the affected service over a time window around the event, together
   with the service topology. This lets the analysis engine tell the root-cause service apart
   from services that only show the symptom.

2. Policy-based safety validator between the LLM and the executor. The LLM outputs a structured
   response plan that is validated against a schema. An action is executed only if it is on an
   action allowlist, its target is a known service, its confidence is at or above a configured
   threshold, it does not violate a cooldown period, and the per-incident action limit has not
   been reached. Otherwise it is routed for human approval or escalated. The LLM never executes
   commands directly.

3. History-aware, bounded re-analysis loop. If verification shows the incident is unresolved,
   the incident is re-analyzed with the attempt number and the list of previously attempted
   actions and their outcomes, so a failed action is not repeated. After a maximum number of
   attempts (e.g., 3), the incident is escalated to a human.

4. Dual detection with a unified incident format and deterministic fallback. Rule-based alerts
   and ML-detected anomalies are converted into one common incident event. Deterministic
   runbooks provide a fallback response, which keeps the system working when the LLM fails, and
   also serve as a non-LLM baseline for comparison.
-----

G. PAGES 5-8: WORKING OF THE INVENTION
-------------------------------------------------------------------------------------
Step 1, Monitoring Data Collection. Add:
-----
In addition to application metrics, the system collects container-level metrics (via a
container metrics exporter such as cAdvisor), dependency metrics (e.g., cache or database
exporters), and the latency of each call from one service to the next (upstream call latency).
-----

Step 2. Rename to "Detection (Rule-based and ML-based)". Keep the rule text and add:
-----
In parallel, a machine-learning anomaly detector polls per-service features (CPU usage, memory
usage ratio, 95th-percentile latency, error rate, request rate and upstream call latency) at
fixed intervals and scores them with a model trained on normal behaviour. It raises an event
only when the anomaly persists for at least two consecutive evaluation windows. Each event
carries the event source (rule or ML), the anomaly score where applicable, the top contributing
features and an incident identifier.
-----

New Step 2a, Event Correlation and Context Building:
-----
Events that arrive within a time window and share a dependency chain are grouped into one
incident. After the first event, the gateway waits for a short settle interval so that events
from the root-cause service and from dependent services showing symptoms are analyzed together.
The context builder then attaches the service topology, the last N minutes of key metrics for
every service in the chain, container state and restart counts, recent actions and the history
of attempts. Ground-truth or fault-labelling signals, where present, are excluded from the
analysis context.
-----

Step 3, Real-Time Event Transmission. Add:
-----
Separate channels are used for incident events and for response plans and action outcomes
(e.g., /ws/events and /ws/responses).
-----

Step 4, Intelligent Incident Analysis. Add:
-----
The prompt includes the service topology and the list of allowed actions. The output is a
structured response plan (root-cause service, incident type, severity, probable cause,
evidence, confidence score, recommended action, fallback action and explanation) and is
validated against a schema. If the LLM times out, is unreachable, returns output that fails
validation or reports a confidence below the threshold, deterministic runbooks produce the
response plan instead.

Safeguards against incorrect or fabricated LLM output include: a constrained action vocabulary
supplied in the prompt; strict schema validation of the output; rejection of unknown services
or actions; a confidence threshold; required evidence fields that cite metrics from the
supplied context; deterministic runbook fallback; and human approval for risky actions.
-----

Step 5, Incident Classification / Decision. Add the criteria (this defines Fig. 2's
"Valid Response?"):
-----
A proposed action is executed automatically only if: (a) the response plan passes schema
validation; (b) the action type is on the allowlist; (c) the target is a known service;
(d) the confidence is a number at or above the threshold (e.g., 0.7); (e) the same action on
the same target has not been taken within the cooldown period (e.g., 5 minutes); (f) the
per-incident action limit (e.g., 3) has not been reached; and (g) the action is not classed as
risky. Risky actions and low-confidence plans are routed for human approval. If the recommended
action is rejected, the plan's fallback action is validated in its place; if neither passes,
the incident is escalated. Immediately before execution, the triggering conditions are checked
again, and the action is withheld if they are no longer active.
-----

Step 6, Response Generation. Remove "Commands or operational actions." Replace with:
-----
Selection of a predefined operational action from an allowlist (e.g., reset a faulty
component, restart a container, flush a cache, change resource limits, escalate to an
operator). Arbitrary shell commands are never executed.
-----

Step 7, Response System. Replace the description with:
-----
The response system has two parts. The policy validator applies the criteria of step 5 to
every response plan, treating each plan as untrusted input regardless of its source. The
executor carries out only allowlisted actions and checks the allowlist again itself. Execution
modes: resetting a faulty component and restarting a container run automatically; flushing a
cache and changing resource limits require human approval; escalation is always allowed and
changes nothing.
-----

Step 8. Rename to "Verification and Re-analysis":
-----
After a settling period (30-60 seconds), the verifier re-evaluates the conditions that fired
and, where applicable, the anomaly score for the root-cause service and the services that
depend on it. If resolved, the incident is closed and its time to resolution recorded. If not
resolved, the incident is re-analyzed with the attempt number increased by one and the list of
previous actions and their outcomes. Only one action per incident is in progress at a time,
and a plan produced for an earlier attempt is discarded. After the maximum number of attempts
(e.g., 3), the incident is escalated to a human operator.
-----

Step 9, Continuous Monitoring. Update the pipeline line to:
-----
Prometheus -> Rules + ML Detector -> Gateway / Context Builder -> WebSocket -> LLM Analysis
(with runbook fallback) -> Policy Validator -> Executor -> Verifier.
-----

I. PAGE 9: "HOW IT WORKS" PARAGRAPH
-------------------------------------------------------------------------------------
-----
The system continuously monitors the infrastructure. Abnormal behaviour is detected either by
a rule-based alert or by the ML anomaly detector, and both produce an event in the same format.
The gateway groups related events into one incident and builds its context from every service
in the dependency chain. The LLM analysis engine receives the context and produces a structured
response plan; if the LLM fails or is not confident, a deterministic runbook produces the plan
instead. The policy validator then checks the proposed action against the allowlist, the known
targets, the confidence threshold, the cooldown and the per-incident action limit; risky
actions go to a human for approval. Approved actions are executed and the verifier checks
whether the incident has been resolved. If it has not, the incident is re-analyzed together
with the actions already attempted, up to a maximum number of attempts, after which it is
escalated to a human operator.
-----

N. SUPPORTING EVIDENCE (for the report; add to the IDF only if the RDC asks for data)
-------------------------------------------------------------------------------------
All numbers from experiments/RESULTS.md (6-7 Oct 2026). Preliminary: one run per scenario.
- Detection: 16 of 16 logged injected faults detected, in 18.3-34.7 s (mean 27.9 s).
- Without automated response a fault lasted its full duration (90-120 s in those runs). With
  it, single faults were fixed in 37.6-48.4 s in development runs (runbook mode).
- Pilot, scenarios 4-7 (latency, errors, Redis stopped, frontend stopped):
    runbooks (B1): root cause 4/4, action correct 4/4, auto-resolved 4/4, mean MTTR 46.0 s
    LLM (B2):      root cause 4/4, action correct 3/4, auto-resolved 4/4, mean MTTR 70.9 s
    unsafe actions executed: 0 in both. The LLM's extra time is its plan latency (about 22 s).
- Offline analyzer comparison on 9 sample incidents, 2 runs each: LLM root cause and action
  18/18 after prompt tuning (optimistic: the prompt was tuned on these samples).
- Re-analysis shown live: after a failed fix the incident was re-analyzed with the attempted
  action in its history, a different action was proposed, the cooldown blocked it, and the
  incident was escalated.
- Pre-execution re-check (claim 8): added after a live run where an alert fired after the fault
  had cleared and caused an unnecessary restart.
- Adversarial safety suite: 29 hallucinated, malformed and malicious plans, 29/29 passed,
  0 unsafe actions executed; 5 are caught only by the policy validator (the LLM output schema
  accepts them), which is the evidence for claim 11.
- Final numbers must come from the full evaluation (all 9 scenarios, at least 20 runs each,
  with the ML detector and a manual baseline). Do not put the pilot numbers in the IDF as
  results.
