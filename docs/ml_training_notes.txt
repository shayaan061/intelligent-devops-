ML DETECTOR: HOW IT WAS TRAINED, WHAT DATA WAS USED, IS THE DATA TOO SMALL
Notes written 13 Oct 2026. Sources: ml/train.py, ml/model.py,
experiments/RESULTS.md sections 12 and 16.


=====================================================================
1. HOW THE ML MODEL WAS TRAINED
=====================================================================

The model was trained only on normal traffic, with no labelled faults.
It learns what "normal" looks like for each service and flags anything
that is worse than that.

1) Training data
   - 78 minutes of normal traffic recorded on 9 Oct (13:34-14:52 UTC),
     with Locust running at 5 users and no faults injected.
   - experiments/record_baseline.py exported the metrics from Prometheus
     and drops any sample near a fault or alert. Here nothing needed
     dropping.
   - Result: experiments/baseline_20261009_1334.csv, 945 rows, 315 per
     service, one sample every 15 s.

2) Features per service
   - frontend and api-service: cpu, mem, p95 latency, error rate,
     requests/s, upstream p95
   - redis: mem, mem_bytes, clients, ops
   - The fault_* ground-truth gauges are never used.

3) The model (one per service, two parts)
   - Robust z-scores. For each metric it stores the median and the MAD
     from training. The score is
       z = (x - median) / max(1.4826 * MAD, floor)
     The floor stops a metric that never moved in training (such as
     err = 0) from flagging every tiny change. Only the "worse"
     direction counts: higher CPU, memory, latency or errors.
   - Isolation Forest. 200 trees fit on the z-score vectors. Its
     threshold is the 99.5% quantile of the training scores, which
     catches unusual combinations of metrics.
   - Decision. A sample is anomalous if any metric has z >= 4, or if the
     forest flags it and some metric has z >= 2.
   - When it reports. After 2 anomalous polls in a row (about 15 s).

4) Validation
   - Each service's data was split in time order. A model trained on the
     first 80% flagged 0 of the 63 held-out normal samples (the last
     20%) for every service.
   - The final model was then refit on all the data and saved to
     ml/models/detector.joblib, with a report in detector_report.json.
   - The thresholds (z 4 / 2, the floors, 2 polls) were chosen before
     any fault runs, not tuned on them.

5) Results
   - Offline replay: caught 8 of 9 scenarios with 0 false alarms.
     Scenario 7 (frontend container stopped) is missed by design,
     because a stopped container reports no metrics; the ServiceDown
     alert covers it.
   - Gradual memory leak (scenario 8): ML detected it in about 51-57 s,
     against 232 s for the alert rule. This is the case the ML detector
     is there for.
   - 10 h soak with no faults (RESULTS.md section 16): 0 false alarms.

Caveat for the report: the model only saw 5-user load.

To retrain:
   python experiments/record_baseline.py --last 2h
   docker compose run --rm ml-detector python train.py /experiments/baseline_<stamp>.csv


=====================================================================
2. WHAT DATA WAS USED
=====================================================================

Metrics recorded from the project's own demo stack during 78 minutes of
normal operation. No public dataset and no fault data were used.

Source
   - File: experiments/baseline_20261009_1334.csv (69 KB)
   - When: 9 Oct 2026, 13:34-14:52 UTC
   - Traffic: the Locust "load" service with 5 simulated users, about
     4.9 requests/s through frontend -> api-service -> redis.
   - Faults: none injected and no alerts fired, so no rows were dropped.
   - How it was made: experiments/record_baseline.py queried Prometheus
     once every 15 s, using the same queries the gateway's context
     builder uses. The underlying data comes from cAdvisor (container
     CPU and memory), the Flask apps' /metrics and redis_exporter.

Shape
   - 945 rows: 315 each for frontend, api-service and redis.
   - Columns: timestamp, service, clients, cpu, err, mem, mem_bytes, ops,
     p95, rps, up, upstream_p95
   - The first ~11 rows per service have blank CPU, latency and rate
     values while the 30 s rate windows filled up, so 304 of 315 rows
     are complete.

Typical (median) values

   Service       cpu    mem (% of limit)  p95 latency  errors  req/s  upstream p95
   frontend      2.5%   8.0%              5.6 ms       0       4.92   5.0 ms
   api-service   1.6%   9.4%              4.7 ms       0       4.92   4.7 ms

   redis: 3.9% memory (1.3 MB), 4 clients, 6.4 ops/s.

Excluded on purpose: the fault_*_active ground-truth gauges, which are
only used for scoring.

Limitations for the report
   - One load level only (5 users).
   - About 78 minutes from one session on one Mac.
   - Errors were always 0, so the error-rate scale relies on its floor
     (0.02) rather than learned variation.

The trained model and its holdout report are in ml/models/detector.joblib
and experiments/results/ml_detector_report_9oct.json.


=====================================================================
3. ISN'T THIS TOO SMALL?
=====================================================================

It is small, but it is less of a problem than it looks, for two reasons.

Why 945 rows is enough for this model
   - The model doesn't learn a complex decision boundary. For each
     metric it learns a typical value (the median) and a typical spread
     (the MAD). Around 300 samples per service is plenty to estimate
     those reliably.
   - The Isolation Forest only fits 6 features per service. A few
     hundred points is a normal training size for that.
   - It is anomaly detection, not classification, so it doesn't need
     fault examples, which is where large datasets usually matter.

The 10 h soak gives stronger evidence than the dataset size
(RESULTS.md section 16)
   - It ran with no faults, but with restarts and load changes from 2 to
     10 users, which are conditions the model never saw in training.
   - The result was 0 false alarms in 10 hours, about 8x longer than the
     training data.
   - That is the real answer to "does it generalise to normal traffic?"

Where it really is weak
   - One load level, one session, one machine. It hasn't seen slow
     drifts, such as memory creeping up over hours.
   - The holdout was only 63 samples per service. "0 flagged" there
     means little on its own; the soak is what backs it up.
   - Error rate was always 0 in training, so that metric depends on its
     hand-set floor.
   - Fault detection was tested on few runs. The replay covered 9
     scenarios and the live runs n = 1-2, though the evaluation stages
     are adding more.

What to do
   - Don't retrain in the middle of the evaluation. Stage 1 and the
     stage 2 runs so far used this model. Changing it now splits the
     results for system S, and you'd have to report two versions or
     rerun.
   - In the report, describe it as "78 min baseline, validated by a 10 h
     fault-free soak with load changes (0 false alarms) and by the
     evaluation runs." List one load level and one session as a
     limitation.
   - If a bigger dataset is wanted, do it before continuing stage 2.
     Record about 2-3 h across 2, 5 and 10 users with
     record_baseline.py, retrain, rerun ml/replay.py and the soak, and
     then use that model for all remaining runs. It costs about half a
     day of machine time, and stage 1 for S would need redoing or
     reporting separately.

Recommendation: keep the current model and use the soak result to
justify it. Retrain only if the guide or reviewers push on the dataset
size.
