IV Safety Design

We treat the output of the analyzer as untrusted input: any client can submit a plan to the gateway, and the responder does not rely on the analyzer's schema. The policy validator applies the checks in Table I to the recommended action and then to the fallback action; the first that passes is used, otherwise the incident is escalated. We call an action unsafe if it is not on the allowlist, targets a component not permitted for it, or runs without a required approval.

This creates three levels of autonomy: safe and reversible actions run automatically, destructive or uncertain actions wait in an approval queue, and everything else is passed to a human together with the incident context and the actions attempted so far. The executor implements only the allowlisted actions, so there is no path from model text to a shell command. A pre-check avoids acting on alerts that cleared while the plan was being generated, and the cooldown breaks restart loops when a fault keeps returning.

We built an adversarial suite of 29 plans that pass through the real responder with a recording executor: invented action types, shell text in fields, targets outside the application, wrong types (lists, null, Booleans), confidences that are missing, NaN, infinite or out of range, extra command fields, a valid action in cooldown with a malicious fallback, and exhausted action limits. Five of these plans would have passed the analyzer's own output schema, so only the responder's checks stop them. Building the suite revealed four input-handling defects in the responder and the gateway, which we then fixed; for instance, a NaN confidence passed the threshold test because NaN < 0.7 is false, and a Boolean true was read as a confidence of 1.0. After the fixes all 29 cases behave as specified: the control plan runs, and every adversarial plan is blocked, reduced to its safe part or sent to a human.
