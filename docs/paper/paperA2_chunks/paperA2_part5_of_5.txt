What the guard contributes. The errors made by the LLM were exactly the kinds the guard was designed for: a weaker action on a known fault, the symptom service blamed for a misleading fault, and a failed action recommended again on re-analysis (45 times in S) although the incident history listed it. In each case the outcome was bounded by the policy layer and the verify loop, not by the model. Safety therefore did not depend on the quality of the model, which matters because an operator cannot verify each recommendation of a model in advance.

Each component has a different role. On known faults the LLM added latency and no accuracy, and on the misleading faults it failed in the same way as the runbooks. On the unknown set it was the only analysis step that resolved the subtle latency fault, and only because the detector had found it first: the detector without the LLM could only escalate, and the LLM without the detector never saw the fault. The detector also prevented the verifier from accepting a restart that had not worked. A deployment should therefore assign known patterns to runbooks, call the LLM when no runbook applies, and keep the same guard for both. The LLM is not a universal fix: for the Redis memory fault it suggested the same useless restart as the runbook.

Validity. Faults are injected through an endpoint, so the reset action stands in for real rollbacks or feature-flag switches. The testbed is a single laptop with three services, synthetic load and one 8-billion-parameter model; a larger model may diagnose the misleading faults better. The unknown set has four scenarios, created by the authors after the first evaluation, so it shows where the LLM can help rather than how often it will. A manual baseline in which an engineer handles the same faults is needed to measure the time saved against current practice. Future work includes error logs and deployment events in the incident context, rollback as an action, fine-tuning the model on logged incidents and testing it on held-out faults, and larger Kubernetes deployments.

VIII. CONCLUSION

We presented a closed-loop incident response system in which a policy layer, not the LLM itself, decides what runs. On real containers no unsafe action was executed in 890 runs or 29 adversarial plans, the verify loop repaired wrong first diagnoses, and misleading or recurring faults were escalated after a bounded number of attempts. On known faults the runbooks outperformed the LLM in both action choice and speed; on faults without a runbook, the detector and the LLM together resolved 18 of 40 runs against 10 for the runbooks. Bounded, verified automation with graded human approval enables operators to use LLMs where runbooks end, without trusting them.
