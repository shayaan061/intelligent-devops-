Scenarios 1-9 comprise the main set of known faults which the runbooks address, lasting 180 s (300 s for the leak). The next set of faulty scenarios 10-14 are misleading, below threshold, and recurring faults and last 300 s (480 s for scenario 14). The third set of unknown faults 15, 16, 18 and 19 did not have a runbook rule written for them and last 300 s: subtle faults in the frontend, two faults simultaneously, and a Redis memory fault. We continued to use the existing rules for 18 and 19, but the Redis memory rule restart will not fix 19. We added this third set after evaluating the first two.

B. Systems Compared

B1: alert rules and runbooks, without LLM or the detector. B2: alert rules and LLM, with runbook fallback, without the detector. B1 and B2 receive the same signals, so the difference between B1 and B2 isolates the analysis step. S: the full system. SF: the full system with the LLM made unavailable so that its runbooks act on the incidents generated by the detector (run on scenarios 3, 4, 6 and 8 and the unknown set). S and SF only differ in the analysis step, while SF and B1 only differ in the detector. The responder and the policies are the same across all variants.

C. Protocol and Metrics

Each round executes every scenario once per system in a character permutation determined by a seed, the runs distributed by system, and 300 s between for each run so the cooldown effect is absent. The fundamental set was run for 20 rounds (180 runs per system), the supplementary set for 10 rounds (190 runs) and the "unknown" set for 10 rounds per each of all 4 variants (160 runs); a run when the laptop was asleep was invalidated and replayed. We report the root-cause accuracy (from the first plan), and whether the implemented action's result matched the predicted one; and the number of unsafe, collateral, and permitted (on a system that was not the cause) actions; the auto-resolution rate; the mean time to recover (MTTR, from error onset until the error is rectified, for successfully remediated runs); the fraction of remediated runs requiring a second action; the escalation rate; and the LLM cost as plan latency and tokens per incident.

VI. RESULTS

A. Safety (RQ1)

In none of the 890 runs of the four variants was an unsafe action played, and no incident was opened without an injected fault. Safety came at a cost: on the deceptive faults of the extra set the variants played 43, 35 and 36 collateral actions (B1, B2, S), resets and restarts of a healthy service that the policy allows, and S played 8 more on the mystery set; the cooldown and the action limit kept these to three per incident. No plan in the live runs suggested a destructive action, so the approval path was only exercised by the hostile suite.

To get an idea of how the policy performed in the wild, we counted its decisions in the 562 incidents held by the incident store (core rounds 5-20, extra rounds 2-10). The allowlist, target and confidence checks never needed to block a live plan: all named a permitted action and target with a reasonable confidence, so the evidence for these checks is the set of adversarial variants. The guard showed up in the cooldown: the LLM variants suggested a restart or reset in the extra set 46 (B2) and 45 (S) times in a row after that reset/restart had just failed, and on all 4 recommended to escalate a certain incident, the cooldown blocked and the responder ran the fallback or escalated. The runbooks never suggested a restart or reset for unmatched incidents, so the plans for unmatched incidents escalate.

B. Known Faults: LLM Versus Runbooks (RQ2)

In the core scenarios (Table III), all variants found all faults. B1 and B2 both identified the root cause for all runs, but B1 executed the correct action 100% of the time, while B2 did 92.2%. For the incorrect actions, they were both all on scenario 5 (6/20 correct) in which the LLM both identified the correct service and restarted that service rather than resetting the fault, and the restart cleared the fault, so while a safe safety action, it cost time.
